## Purpose

约束可配置 SSO 存储的升级、兼容发布、回滚和验收过程，确保四个站点使用相容的凭证命名空间与代理能力，并以真实浏览器和既有后端联调结果证明行为。该能力同时防止旧凭证在回滚中复活、诊断泄露凭证以及未经真机验证就宣称移动端问题已经修复。

## ADDED Requirements

### Requirement: 凭证版本与代理协议分阶段激活

系统 SHALL 通过 `NEXT_PUBLIC_SSO_CREDENTIAL_VERSION` 显式选择凭证版本，只接受 1 或 2，未配置时默认为 1。版本 1 MUST 保持原 LOCAL、SESSION 行为及原 key；版本 2 SHALL 激活本地优先、新会话生命周期及 `:v2` 凭证命名空间。COOKIE MUST 仅在版本 2 使用。代理协议 v2 SHALL 可以先于凭证版本 2 发布，MUST 不因代理升级而提前改变凭证 key 或读取行为。`NEXT_PUBLIC_TOKEN_KEY` SHALL 保持原始基础 key，由版本规则产生实际名称，不要求部署者手工追加 `:v2`。

#### Scenario: 未配置凭证版本
- **WHEN** 新代码发布时尚未配置凭证版本，或明确配置为 1
- **THEN** LOCAL、SESSION 继续使用旧 key 和原有读取路线，不提前启用本地优先或强制重登

#### Scenario: 先升级代理协议
- **WHEN** 普通及 debug 代理已升级至协议 v2，而四站凭证版本仍为 1
- **THEN** 旧 LOCAL/SESSION 的 GET、SET、REMOVE 保持兼容，登录与退出仍可用，代理升级本身不激活 COOKIE 或新命名空间

#### Scenario: 版本 1 配置 Cookie
- **WHEN** 凭证版本为 1，却通过默认配置或显式调用选择 COOKIE
- **THEN** 系统返回明确配置或能力错误，不静默激活版本 2，也不回退 LOCAL

#### Scenario: 配置不支持的凭证版本
- **WHEN** 凭证版本配置非空且不是 1 或 2
- **THEN** 系统拒绝该配置，不猜测应使用旧凭证还是新凭证

#### Scenario: 激活新命名空间
- **WHEN** 四站激活凭证版本 2，环境配置仍使用原始基础 token key
- **THEN** 实际登录凭证 key 使用该基础 key 的 `:v2` 命名空间，不读取基础 key，也不要求手工重复追加版本后缀

### Requirement: 激活新凭证命名空间要求重新登录

系统 SHALL 在正式激活本变更时统一使用新的凭证命名空间并要求重新登录，MUST 不读取、导入或迁移旧 token 来恢复登录体验。用户资料缓存及访客凭证 SHALL 与新的命名空间一致；激活前的兼容准备阶段与激活后的行为 MUST 明确区分。

#### Scenario: 激活时浏览器仍有旧 LOCAL token
- **WHEN** 新命名空间正式激活，而用户浏览器仍保存此前的 LOCAL 登录凭证
- **THEN** 新前端不读取或复制该旧 token，用户需要重新登录

#### Scenario: 浏览器仅有旧用户缓存或访客凭证
- **WHEN** 新版本加载时存在旧命名空间的用户资料或访客凭证
- **THEN** 它们不能使新版本恢复旧用户身份或跳过新的真实登录查询

#### Scenario: 激活前的协议兼容准备
- **WHEN** 发布处于升级代理与客户端能力的准备阶段，尚未激活新命名空间和 COOKIE
- **THEN** 既有 LOCAL、SESSION 兼容行为可以继续使用，但该阶段不能被报告为已完成强制重登切换

### Requirement: 四站配置与代理能力一致性

发布过程 MUST 在激活前验证 www、admin、im、passport 的协议版本、凭证命名空间、存储模式、代理 origin 和 Cookie 共享属性相容。配置不一致、生产非安全配置或代理能力不足时 MUST 阻止激活，不允许由某个站点静默降级来掩盖不兼容。

#### Scenario: 四站配置一致且代理就绪
- **WHEN** 四站的发布信息一致，且正常与 debug 代理均支持所需的存储及条件更新能力
- **THEN** 发布可以进入新命名空间及 COOKIE 的激活阶段

#### Scenario: 应用站提前使用 Cookie
- **WHEN** 任一应用站准备激活 COOKIE，但认证站代理尚未具备所需能力
- **THEN** 发布阻止该不兼容组合的激活，不依靠请求超时或 LOCAL 回退继续上线

#### Scenario: Cookie 或命名空间配置不一致
- **WHEN** 四站在凭证命名空间、共享 Domain、SameSite、Secure 或所选模式上出现不兼容差异
- **THEN** 发布校验明确失败并指出配置类别，不输出实际凭证

#### Scenario: 四站替换存在时间窗口
- **WHEN** 四站部署无法在同一个瞬间完成替换
- **THEN** 发布期间仍保持协议兼容，不提前激活依赖未完成站点的新凭证行为

### Requirement: 回滚不得复活已退役凭证

系统 MUST 保留不随站点历史包覆盖而回退的凭证命名空间约束，并拒绝部署会重新启用已退役 key 的历史包。需要回退代码时 SHALL 使用当前有效命名空间重新构建兼容产物，不得通过重新读取旧 LOCAL、SESSION 或 Cookie 凭证恢复登录。

#### Scenario: 历史包使用已退役 key
- **WHEN** 回滚目标会恢复已退役凭证命名空间
- **THEN** 发布拒绝该历史包，即使它是时间上最近的上一版本

#### Scenario: 旧代码以当前命名空间重新构建
- **WHEN** 回退产物使用当前有效命名空间并满足现有协议与存储兼容条件
- **THEN** 发布可以接受该兼容回退，且浏览器中的旧命名空间 token 不会重新被读取

### Requirement: 已打开旧页面的强制失效联调

发布验收 SHALL 区分新前端不读取旧 key 与已打开旧页面的会话失效。要求全员重新登录的激活 SHALL 联调用户已确认的后端统一凭证失效能力；MUST 不将仅修改前端 key 作为已打开旧页面立即失效的证明，也 MUST 不新增另一套后端注销机制。

#### Scenario: 旧页面仍运行已加载脚本
- **WHEN** 新版本激活时用户仍打开旧前端页面并持有旧 token 或旧 WebSocket
- **THEN** 联调验证既有后端统一能力使旧会话失效，不能仅以新页面已使用新 key 判定通过

#### Scenario: 只有前端构建验证完成
- **WHEN** 尚未取得旧会话 HTTP、上传及 WebSocket 失效的联调证据
- **THEN** 验收不得将严格全员重登要求标记为已通过

### Requirement: 后端字段及续期契约必须经过真实映射验证

凭证版本 2 上线前 SHALL 固定现有登录和续期接口的实际字段、时间单位、记住我策略及业务截止映射，并使用脱敏真实响应验证。验收 MUST 证明仅凭签名 token 即可重建会话身份、签发时间、业务截止、续期时机和记住我策略，且响应元数据与 token 一致。后端统一鉴权和注销保证 SHALL 作为已有能力接入；相邻仓库源码、前端模拟或假定接口路径 MUST 不被用来代替线上接入契约。

#### Scenario: 记住我字段存在命名差异
- **WHEN** 页面字段与后端实际接收字段名称不同
- **THEN** 联调证明用户的布尔选择被正确传递，并由后端返回对应有效策略

#### Scenario: 续期字段或时间单位无法确认
- **WHEN** 无法从真实契约确认业务截止、会话身份、续期时机或时间单位
- **THEN** 凭证版本 2 不得开放生产发布，不能以猜测字段或模拟测试替代缺失的验证

#### Scenario: 元数据仅存在于登录响应
- **WHEN** 真实登录响应包含所需字段，但刷新页面后无法仅从 token 重建全部必要元数据
- **THEN** 凭证版本 2 的接入契约验收失败，即使首次登录及 COOKIE 写入成功也不能发布

#### Scenario: 14 天业务截止与第 15 天保留
- **WHEN** 联调使用默认业务 14 天的凭证，并覆盖业务截止前、截止时及额外保留日
- **THEN** 证据显示业务截止前按后端策略续期，截止后必须重新登录，额外保留日没有使用或续期权限

### Requirement: 移动端及存储边界验收

发布 SHALL 至少通过真机 iOS Safari 与 Android Chrome 普通模式的同浏览器、HTTPS 同根域跨子域 COOKIE 验收，并记录浏览器版本、隐私设置及日期。不同根域 SHALL 记录尽力读取结果，不承诺第三方存储受限环境下静默 SSO；不同浏览器共享不在本变更保证范围内。

#### Scenario: 关闭第三方 Cookie 的同根域测试
- **WHEN** 同一浏览器的认证站与应用站正确配置共享父域 Cookie，且第三方 Cookie 被限制
- **THEN** 应用站仍通过本地共享 Cookie 完成跨子域登录态读取，不依赖 iframe 来满足该必须通过项

#### Scenario: 不同根域允许代理访问
- **WHEN** 真机浏览器允许不同根域代理访问目标存储
- **THEN** 验证 RPC 可以读取凭证且不在 B 留副本，并将结果标记为该测试环境下通过

#### Scenario: 不同根域拒绝或隐藏代理 Cookie
- **WHEN** 浏览器限制导致代理无法访问目标 Cookie，或静默返回空值
- **THEN** 验收保留真实结果，不将该环境标为保证支持，也不宣称可以绕过浏览器限制

#### Scenario: 只有模拟浏览器测试结果
- **WHEN** 只完成桌面移动视口或自动化 WebKit 测试
- **THEN** 不能代替真机移动端通过证据，也不能据此宣称线上手机故障已经修复

#### Scenario: 浏览器提前清理持久 Cookie
- **WHEN** 浏览器隐私策略在配置保存截止前清理 Cookie
- **THEN** 系统正确处理凭证缺失，产品与验收结论不承诺浏览器必然保存满 14 天或 15 天

### Requirement: 高风险会话一致性回归

发布验收 MUST 覆盖本地命中、RPC 不回写、来源一致续期、访客隔离、迟到响应、旧用户缓存和既有 WebSocket。LOCAL 与 SESSION 的显式参数及错误语义 SHALL 与新增 COOKIE 一并回归；只验证普通登录成功 MUST 不足以通过本变更验收。

#### Scenario: RPC 来源续期及保存失败
- **WHEN** 对 A 来源凭证执行成功续期与 A 拒写两种测试
- **THEN** 两种情况下 B 均不新增 token 副本，成功结果只更新 A，拒写被明确报告

#### Scenario: 退出与慢请求竞态
- **WHEN** 退出或新登录发生在旧 RPC、续期或访客生成完成之前
- **THEN** 旧结果不能恢复失效身份、删除新身份或覆盖新登录

#### Scenario: B 已有访客而 A 登录真实用户
- **WHEN** 应用站已有访客凭证，随后认证站完成真实登录
- **THEN** 回归证明访客不会阻止真实登录查询，也不会覆盖认证站登录凭证

#### Scenario: Cookie 错误与模式回归
- **WHEN** 测试 Cookie 特殊字符、同名重复、超长、拒写、删除残留及三种显式存储选择
- **THEN** 系统返回预期结果或明确错误，不假报登录成功，不暗中切换模式

### Requirement: 诊断与验收证据必须脱敏

系统 SHALL 提供足以区分配置错误、存储失败、代理等待、超时、能力不支持及会话变化的诊断信息。生产、debug 代理、显式监控及验收记录 MUST 不输出完整 token、Cookie、Authorization 或完整用户资料；诊断开关 MUST 不改变认证行为。

#### Scenario: 调试代理处理真实登录凭证
- **WHEN** 显式开启调试或监控并执行读取、写入、续期及删除
- **THEN** 日志可以关联操作与错误类别，但不能包含可重放凭证或完整用户资料

#### Scenario: 相同请求在普通与 debug 代理执行
- **WHEN** 同一合法请求分别经过普通代理与 debug 代理
- **THEN** 两者的权限校验、存储结果和失败语义一致，仅诊断展示不同

#### Scenario: 记录移动端失败证据
- **WHEN** 测试人员保存跨根域失败、超时或失效会话的验收材料
- **THEN** 材料包含环境及失败类别，但不保留真实 token、完整 Cookie 或 Authorization 内容
